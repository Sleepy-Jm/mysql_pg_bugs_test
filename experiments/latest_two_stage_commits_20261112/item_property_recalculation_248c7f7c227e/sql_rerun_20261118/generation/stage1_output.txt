1. How to reach the modified path

The supplied caller is the scalar-subquery-to-derived-table transform. A candidate SQL structure is an expression `E` in `WHERE`, `JOIN`/`ON`, `HAVING`, or the `SELECT` list that contains a scalar subquery and is rooted at an `Item_func` or `Item_func_isnull`. The resolver records the subquery location and calls `Query_block::replace_subquery_in_expr` on the containing expression pointer (`sql_resolver.cc:7654-7693`). That call is guarded by `(*expr)->has_subquery()` (`sql_resolver.cc:6515`), so before replacement the expression object must already have `PROP_SUBQUERY` accumulated. The helper may unwrap a rollup group wrapper, then replaces the scalar subquery with a derived-table field through `transform`, stores the result back at `*expr`, and calls `new_item->update_used_tables()` (`sql_resolver.cc:6524-6545`).

For the changed base operation, `new_item` must be an `Item_func` whose old argument tree contained the scalar subquery. Virtual dispatch enters `Item_func::update_used_tables` at `sql/item_func.cc:708`. The target resets `m_accum_properties = 0` before looping over arguments; it then calls each child’s `update_used_tables()`, ORs `used_tables_cache` and, when `null_on_null`, `not_null_tables_cache`, and calls `add_accum_properties(args[i])`. To exercise the reset, the pre-transform item must carry a property that no post-transform child still carries. The canonical case is stale `PROP_SUBQUERY` after a scalar subquery has been replaced by a field. The chain is bypassed if `has_subquery()` is false before replacement, if the transform returns null, or if the subquery’s location does not pass one of the listed expression pointers.

For the changed `Item_func_isnull` operation, the SQL shape is `(expr) IS NULL`, and the containing item is `Item_func_isnull` with `args[0] = expr`. The same replacement path can call `update_used_tables()` on this item after a scalar subquery inside `expr` is replaced. In the target, `Item_func_isnull::update_used_tables()` unconditionally executes `args[0]->update_used_tables()` and `set_accum_properties(args[0])` before checking `args[0]->is_nullable()` (`sql/item_cmpfunc.cc:5957-5965`). The moved branch is distinct when `args[0]->is_nullable()` is false: parent skipped the child update and property copy, while target performs both and then sets `used_tables_cache = 0`.

For the added rollup override, a `SELECT`-list expression subject to `WITH ROLLUP` can be wrapped by `Item_rollup_group_item`. The replacement loop unwraps the wrapper before calling `replace_subquery_in_expr` and keeps the wrapper intact (`sql_resolver.cc:6524-6527`, `7687-7692`). After replacement, `new_item->update_used_tables()` dispatches to `Item_rollup_group_item::update_used_tables()` (`sql/item_func.h:1635-1638`). That override calls the changed base, which now clears `m_accum_properties`, and then calls `set_rollup_expr()`, preserving `PROP_ROLLUP_EXPR` on the wrapper.

The main established link is: SQL expression position -> containing `Item` pointer -> `replace_subquery_in_expr` -> `new_item->update_used_tables()` -> virtual modified operation. The parser-to-concrete-`Item` binding is a construction hypothesis unless the resolved item type is observed for the specific SQL shape.

2. Sensitive inputs and possible errors after reaching that path

C1: Rooted `Item_func` containing a scalar subquery that is replaced by a derived-table field.

SQL structure: `F(..., scalar_subquery, ...)` in a replaced position, e.g. a comparison or arithmetic expression. Object path: the outer `Item_func` is the same `*expr` passed to `replace_subquery_in_expr`; after replacement, its child is a field without `PROP_SUBQUERY`. Sensitive property: `m_accum_properties` on the outer `Item_func`. Parent operation: `Item_func::update_used_tables` does not clear `m_accum_properties`, so the old `PROP_SUBQUERY` remains even after the child is replaced. Target operation: `m_accum_properties = 0` is set, then only current child properties are added again. Semantic difference: parent can continue to report `has_subquery() == true` for an expression tree that no longer contains a subquery; target recomputes it as false. Downstream consumers of `has_subquery()` may therefore take different transform/rewrite paths. SQL-visible observation is a different plan or transform result after scalar-subquery replacement; the independent oracle is that the post-replacement tree should not contain a subquery, and the evaluated result should match the original scalar subquery evaluated through the derived table. Source basis: `sql_resolver.cc:6515`, `6545`; target `sql/item_func.cc:708-719`; parent `sql/item_func.cc:708-718`. This is an established difference, but the direction is parent-side staleness; no target-side semantic violation is established from this item alone.

C2: `Item_in_optimizer` wrapping an `IN` subquery may lose its self-set `PROP_SUBQUERY`.

SQL structure: `outer_expr IN (SELECT ...)` or `NOT IN`. Object path: the SQL expression resolves to an `Item_in_optimizer` whose constructor calls `set_subquery()` (`sql/item_cmpfunc.h:500-504`). When `Item_in_optimizer::update_used_tables()` runs, it calls `Item_func::update_used_tables()` and does not call `set_subquery()` afterward (`sql/item_cmpfunc.cc:2410-2419`). Target’s base reset clears `PROP_SUBQUERY`; restoration now depends entirely on `args[0]->m_accum_properties` after `Item_in_subselect::update_used_tables()`. The supplied `Item_in_subselect::update_used_tables()` does not show a `set_subquery()` call; it only updates used tables and the left expression (`sql/item_subselect.cc:2537-2541`). If the omitted `Item_subselect::update_used_tables()` does not leave `PROP_SUBQUERY` set on `args[0]`, target makes `Item_in_optimizer::has_subquery()` false. Downstream, a guard such as the one at `sql_resolver.cc:6515` or other subquery-specific transforms could then skip handling for an item that still semantically contains an `IN` subquery. SQL-visible observation would be a missing or different subquery transform for such a predicate; the independent oracle is ordinary `IN` subquery semantics. Source basis: `item_cmpfunc.h:500-504`, `item_cmpfunc.cc:2410-2419`, `item_func.cc:708-719`, `item_subselect.cc:2537-2541`. Unresolved step: whether `Item_subselect::update_used_tables()` preserves or resets `PROP_SUBQUERY`. This is a target-side hypothesis, not established.

C3: Window-function property under an ordinary `Item_func` or `Item_func_isnull` may be cleared or newly propagated, changing window materialization.

SQL structure: top-level expression containing a window function under a container, e.g. `g(WF)` or `(WF) IS NULL`, where `WF` is a window function such as a windowed aggregate. Object path: the container item is subject to the same `update_used_tables()` path; later, window output processing calls `CreateFramebufferTable()`. That function checks `orig_item->has_wf()` on each source field and removes fields marked as containing a window function from the framebuffer (`sql/sql_select.cc:4106-4122`). It also applies `ReplaceMaterializedItems` only when `ptr.func()->has_wf()` (`sql_select.cc:4139-4144`). Sensitive property: `PROP_WINDOW_FUNCTION` on the container or source item. Operation difference: target’s base reset and the `Item_func_isnull` move can change whether that bit is copied from the window-function child into the container. If the child window function does not itself retain `PROP_WINDOW_FUNCTION` through its own `update_used_tables()` (not supplied), the target reset can produce a false-negative `has_wf()` on the container, causing the field to be included in the framebuffer or its materialized-item replacement to be skipped. The possible SQL-visible violation is a window query returning incorrect restored values or evaluating the window function against the wrong input rows. The independent oracle is that the window expression must be evaluated after framebuffering with its arguments rewritten to the output table, as described in `sql_select.cc:4133-4144`. Source basis: `item_func.cc:708-719`, `item_cmpfunc.cc:5957-5965`, `sql_select.cc:4106-4145`. Unresolved step: the update behavior of the window-function item itself and the exact failure mode of `ReplaceMaterializedItems` when `has_wf()` is false. This is a target-side hypothesis.

C4: `IS NULL` over a non-nullable child carrying aggregated/window property now propagates that property where parent did not.

SQL structure: `(expr) IS NULL` with `expr` non-nullable but containing an aggregate or window function. Object path: `Item_func_isnull::update_used_tables()` reaches the moved propagation in target (`args[0]->update_used_tables(); set_accum_properties(args[0])`) before the `used_tables_cache = 0` branch. Parent skipped propagation when `args[0]->is_nullable()` was false. Sensitive property: `PROP_AGGREGATION` or `PROP_WINDOW_FUNCTION` on the `IS NULL` item. Operation difference: target marks the `IS NULL` container with the child’s accumulated property; parent does not. This can change downstream consumers such as `replace_subquery_in_expr`’s `split_sum_func` decision (`sql_resolver.cc:6549-6553`) or `CreateFramebufferTable`’s `has_wf()` filtering. SQL-visible observation is a different treatment of an aggregate/window expression wrapped in a constant-false `IS NULL`. Independent oracle: the item still contains the aggregate/window function and should be subject to the same splitting/materialization rules as any other expression containing one. Source basis: target `item_cmpfunc.cc:5957-5970`; parent `item_cmpfunc.cc:5957-5971`; `sql_resolver.cc:6549-6553`; `sql_select.cc:4114-4145`. This is an established difference; whether target creates a semantic violation depends on downstream behavior that is not fully supplied, but the excerpted consumers are consistent with the target propagation being intentional.
