1. Construction realization

The Stage 1 handoff establishes the following chain: a SQL expression position containing a scalar subquery resolves to a containing `Item` pointer; `replace_subquery_in_expr` is called on that pointer; the scalar subquery is replaced by a derived-table field; `new_item->update_used_tables()` is invoked; virtual dispatch reaches the modified `Item_func::update_used_tables` (and, for `IS NULL`, `Item_func_isnull::update_used_tables`). The parser-to-concrete-`Item` binding for each SQL shape remains a construction hypothesis unless the resolved item type is observed.

Supported mappings (source-backed):
- C1: outer `Item_func` rooted at a comparison/arithmetic expression containing a scalar subquery in a replaced position. The sensitive property is `m_accum_properties` on that outer `Item_func`; the target resets it and re-accumulates from current children. The SQL-visible observation is a plan/transform difference after replacement; the independent oracle is that the post-replacement tree no longer contains a subquery and the evaluated result matches the original scalar-subquery semantics.
- C2: `outer_expr IN (SELECT ...)` / `NOT IN` resolving to `Item_in_optimizer`. The sensitive property is `PROP_SUBQUERY` on the optimizer wrapper; target reset may clear it if `args[0]` does not re-set it. Unresolved: whether `Item_subselect::update_used_tables()` preserves `PROP_SUBQUERY`. This is a target-side hypothesis; the SQL test is exploratory.
- C3: window function under an ordinary `Item_func` or `Item_func_isnull` container. Sensitive property is `PROP_WINDOW_FUNCTION` on the container; downstream `CreateFramebufferTable` checks `has_wf()`. Unresolved: update behavior of the window-function item itself and exact failure mode of `ReplaceMaterializedItems`. Exploratory.
- C4: `(expr) IS NULL` where `expr` is non-nullable but contains an aggregate or window function. Target unconditionally calls `args[0]->update_used_tables()` and `set_accum_properties(args[0])` before the `is_nullable()` check; parent skipped both. Sensitive property is `PROP_AGGREGATION`/`PROP_WINDOW_FUNCTION` on the `IS NULL` item. Established difference; downstream semantic violation depends on consumers not fully supplied.

Implementation candidates (not source-confirmed for the specific SQL shape):
- The exact `Item` class produced for `(SELECT ...) + 1`, `(SELECT ...) IS NULL`, `x IN (SELECT ...)`, and `g(WF)` in the tested positions.
- Whether the resolver actually routes each shape through `replace_subquery_in_expr` at the listed pointers for the tested query block.
- Whether `Item_subselect::update_used_tables()` preserves `PROP_SUBQUERY` (C2).
- Whether the window-function item retains `PROP_WINDOW_FUNCTION` through its own `update_used_tables()` (C3).

Five distinct target tests are provided below. T1 and T2 exercise C1 with different operand relationships (arithmetic vs. comparison, and a NULL-sensitive operand). T3 exercises C2 (IN-subquery wrapper). T4 exercises C3 (window function under an ordinary container). T5 exercises C4 (`IS NULL` over a non-nullable aggregate/window child). Each is a distinct candidate; T3–T5 are labeled exploratory where Stage 1 leaves the mapping unresolved.

2. SQL

```sql
-- T1: C1 — outer Item_func (arithmetic) containing a scalar subquery
-- Sensitive operand: the scalar subquery value reaches the outer Item_func
-- via the derived-table field after replacement. Use a negative value so
-- the arithmetic result differs from a naive positive-only assumption.
CREATE TEMPORARY TABLE t1_outer (id INT PRIMARY KEY, k INT NOT NULL);
INSERT INTO t1_outer VALUES (1, 10), (2, 20), (3, 30);
CREATE TEMPORARY TABLE t1_inner (k INT NOT NULL, v INT NOT NULL);
INSERT INTO t1_inner VALUES (10, -7), (20, 5), (30, 0);

SELECT id, k, (SELECT v FROM t1_inner WHERE t1_inner.k = t1_outer.k) + 1 AS r
FROM t1_outer
ORDER BY id;

-- Contrast: same shape but with a positive-only inner value, to show the
-- outer Item_func sees the replaced field value, not a stale subquery.
SELECT id, k, (SELECT v FROM t1_inner WHERE t1_inner.k = t1_outer.k AND v > 0) + 1 AS r
FROM t1_outer
ORDER BY id;

DROP TEMPORARY TABLE t1_inner;
DROP TEMPORARY TABLE t1_outer;
```

```sql
-- T2: C1 — outer Item_func (comparison) with a NULL-producing scalar subquery
-- Sensitive operand: the replaced field can be NULL; the comparison must
-- evaluate against the derived-table field, not a stale subquery marker.
CREATE TEMPORARY TABLE t2_outer (id INT PRIMARY KEY, k INT NOT NULL);
INSERT INTO t2_outer VALUES (1, 10), (2, 20), (3, 30);
CREATE TEMPORARY TABLE t2_inner (k INT NOT NULL, v INT NULL);
INSERT INTO t2_inner VALUES (10, NULL), (20, 5), (30, 0);

SELECT id, k, ((SELECT v FROM t2_inner WHERE t2_inner.k = t2_outer.k) > 0) AS r
FROM t2_outer
ORDER BY id;

-- Contrast: IS NULL over the same replaced scalar subquery, exercising the
-- Item_func_isnull container on the same replaced field.
SELECT id, k, ((SELECT v FROM t2_inner WHERE t2_inner.k = t2_outer.k) IS NULL) AS r
FROM t2_outer
ORDER BY id;

DROP TEMPORARY TABLE t2_inner;
DROP TEMPORARY TABLE t2_outer;
```

```sql
-- T3: C2 (exploratory) — Item_in_optimizer wrapping an IN subquery
-- Sensitive property: PROP_SUBQUERY on the Item_in_optimizer wrapper.
-- Target reset may clear it if args[0] does not re-set it. Use a NOT IN
-- with a NULL in the subquery result to exercise the three-valued branch.
CREATE TEMPORARY TABLE t3_outer (id INT PRIMARY KEY, x INT NULL);
INSERT INTO t3_outer VALUES (1, 1), (2, 2), (3, NULL), (4, 4);
CREATE TEMPORARY TABLE t3_inner (y INT NULL);
INSERT INTO t3_inner VALUES (1), (NULL), (3);

SELECT id, x, x IN (SELECT y FROM t3_inner) AS r
FROM t3_outer
ORDER BY id;

-- Contrast: NOT IN over the same subquery; NULL in the subquery makes the
-- result UNKNOWN for non-matching rows, exercising the wrapper's branch.
SELECT id, x, x NOT IN (SELECT y FROM t3_inner) AS r
FROM t3_outer
ORDER BY id;

DROP TEMPORARY TABLE t3_inner;
DROP TEMPORARY TABLE t3_outer;
```

```sql
-- T4: C3 (exploratory) — window function under an ordinary Item_func container
-- Sensitive property: PROP_WINDOW_FUNCTION on the container; downstream
-- CreateFramebufferTable checks has_wf(). Use a windowed SUM over a
-- partitioned, ordered input so materialization is required.
CREATE TEMPORARY TABLE t4_wf (id INT PRIMARY KEY, g INT NOT NULL, v INT NOT NULL);
INSERT INTO t4_wf VALUES (1, 1, 10), (2, 1, 20), (3, 2, 5), (4, 2, 7);

SELECT id, g, v,
       SUM(v) OVER (PARTITION BY g ORDER BY id) + 1 AS r
FROM t4_wf
ORDER BY id;

-- Contrast: IS NULL over the same windowed expression, exercising the
-- Item_func_isnull container over a window-function child.
SELECT id, g, v,
       (SUM(v) OVER (PARTITION BY g ORDER BY id) + 1) IS NULL AS r
FROM t4_wf
ORDER BY id;

DROP TEMPORARY TABLE t4_wf;
```

```sql
-- T5: C4 — IS NULL over a non-nullable aggregate child
-- Sensitive property: PROP_AGGREGATION on the IS NULL item. Target
-- unconditionally propagates args[0]'s accumulated properties before the
-- is_nullable() check; parent skipped propagation when args[0] was
-- non-nullable. Use a constant-false IS NULL over a non-nullable aggregate.
CREATE TEMPORARY TABLE t5_agg (id INT PRIMARY KEY, g INT NOT NULL, v INT NOT NULL);
INSERT INTO t5_agg VALUES (1, 1, 10), (2, 1, 20), (3, 2, 5), (4, 2, 7);

SELECT g, (SUM(v) IS NULL) AS r
FROM t5_agg
GROUP BY g
ORDER BY g;

-- Contrast: same aggregate without the IS NULL wrapper, to show the
-- aggregate value itself is non-NULL and the IS NULL result is constant false.
SELECT g, SUM(v) AS s
FROM t5_agg
GROUP BY g
ORDER BY g;

DROP TEMPORARY TABLE t5_agg;
```

3. Expected results and path observations

T1 (C1, arithmetic outer `Item_func`):
- Target query: rows (1,10,-6), (2,20,6), (3,30,1). The negative inner value -7 must reach the outer `+ 1` through the replaced derived-table field; a stale `PROP_SUBQUERY` on the outer item would not change the arithmetic result but could change downstream transform decisions.
- Contrast: rows (1,10,1), (2,20,6), (3,30,1) — the `v > 0` filter excludes -7 and 0, so only k=20 contributes 5+1=6; k=10 and k=30 yield NULL+1=NULL. Wait: with `v > 0`, k=10 has no row → scalar subquery NULL → NULL+1 = NULL; k=30 has v=0 excluded → NULL. So contrast rows are (1,10,NULL), (2,20,6), (3,30,NULL). This contrast distinguishes the replaced-field value from a stale subquery marker only via plan/transform observation, not via the arithmetic result alone.
- To confirm the intended object reaches the target branch: observe that the outer `Item_func` for `(SELECT ...) + 1` is the `*expr` passed to `replace_subquery_in_expr`, that its child after replacement is a derived-table field without `PROP_SUBQUERY`, and that `new_item->update_used_tables()` dispatches to `Item_func::update_used_tables`. A plan clue or matching arithmetic alone does not establish the object mapping.

T2 (C1, comparison outer `Item_func` + `IS NULL` container):
- Target query: rows (1,10,NULL), (2,20,1), (3,30,0). NULL > 0 is NULL; 5 > 0 is 1; 0 > 0 is 0.
- Contrast: rows (1,10,1), (2,20,0), (3,30,0). NULL IS NULL is 1; 5 IS NULL is 0; 0 IS NULL is 0.
- Path observation: confirm the comparison item and the `Item_func_isnull` item are the `*expr` pointers passed to `replace_subquery_in_expr`, and that after replacement their child is a field. For the `IS NULL` case, observe whether `args[0]->is_nullable()` is false (the replaced field from a scalar subquery is nullable in general, so this branch may not be the moved one; the moved branch requires a non-nullable child, which T5 targets more directly).

T3 (C2, exploratory `Item_in_optimizer`):
- Target query: rows (1,1,1), (2,2,NULL), (3,NULL,NULL), (4,4,0). 1 IN {1,NULL,3} = 1; 2 IN {1,NULL,3} = NULL; NULL IN ... = NULL; 4 IN ... = 0.
- Contrast: rows (1,1,0), (2,2,NULL), (3,NULL,NULL), (4,4,1). 1 NOT IN {1,NULL,3} = 0; 2 NOT IN ... = NULL; NULL NOT IN ... = NULL; 4 NOT IN ... = 1.
- Path observation: confirm the predicate resolves to `Item_in_optimizer` and that `Item_in_optimizer::update_used_tables()` calls `Item_func::update_used_tables()`. The unresolved step is whether `Item_subselect::update_used_tables()` leaves `PROP_SUBQUERY` set on `args[0]`; if not, target makes `has_subquery()` false on the wrapper. Observe `has_subquery()` on the wrapper before and after `update_used_tables()`, and whether any downstream subquery-specific transform is skipped. The IN/NOT IN results themselves are the independent oracle and must match ordinary semantics regardless of the property bit.

T4 (C3, exploratory window under ordinary container):
- Target query: rows (1,1,10,11), (2,1,20,31), (3,2,5,6), (4,2,7,13). Windowed SUM partitioned by g ordered by id: g=1 → 10, 30; +1 → 11, 31. g=2 → 5, 12; +1 → 6, 13.
- Contrast: rows (1,1,10,0), (2,1,20,0), (3,2,5,0), (4,2,7,0). The windowed expression is non-NULL, so `IS NULL` is 0 for all rows.
- Path observation: confirm the container item is the `*expr` passed to `replace_subquery_in_expr` (if a scalar subquery is present) or otherwise reaches `update_used_tables()`; confirm `CreateFramebufferTable` checks `orig_item->has_wf()` on the source field and that `ReplaceMaterializedItems` is applied when `ptr.func()->has_wf()`. The unresolved step is whether the window-function item retains `PROP_WINDOW_FUNCTION` through its own `update_used_tables()`; if not, the container's `has_wf()` may be false and the field may be included in the framebuffer or materialized-item replacement skipped. Observe the framebuffer contents and whether the windowed values are restored correctly.

T5 (C4, `IS NULL` over non-nullable aggregate):
- Target query: rows (1,0), (2,0). `SUM(v)` per group is non-NULL (10+20=30, 5+7=12), so `SUM(v) IS NULL` is 0 for both groups.
- Contrast: rows (1,30), (2,12). Confirms the aggregate is non-NULL, so the `IS NULL` result is constant false.
- Path observation: confirm the `IS NULL` item is `Item_func_isnull` with `args[0]` being the aggregate item, that `args[0]->is_nullable()` is false, and that target executes `args[0]->update_used_tables()` and `set_accum_properties(args[0])` before the `is_nullable()` check. Observe `m_accum_properties` on the `IS NULL` item: target should carry `PROP_AGGREGATION` from the child; parent should not. Downstream, observe whether `split_sum_func` or `CreateFramebufferTable` treats the `IS NULL` container differently. The result values themselves are the independent oracle and must be 0 in both versions; the difference is in the accumulated property, not the evaluated value.

No execution or instrumentation is claimed. The expected rows above are derived from SQL semantics and the supplied data, independently of either version's output. A valid execution, a target-path observation (the intended `Item` reaching the modified branch), and a parent/target output difference are distinct; matching outputs alone do not establish the object mapping.
