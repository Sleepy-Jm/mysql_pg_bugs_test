1. Construction realization

Stage 1 supplies three candidate relationships (C1, C2, C3). Only C1 and C2 have a source-supported link from the modified `update_used_tables()` to a downstream consumer (`has_subquery()` residual handling is not shown; `has_wf()` in `CreateFramebufferTable()`/`ReplaceMaterializedItems()` is shown). C3 is a preservation invariant with no established downstream consumer, so it cannot be turned into a target test that distinguishes parent from target; it is retained as an unresolved mapping and not counted.

Supported mappings (source-backed):
- C1: `replace_subquery_in_expr` guard `(*expr)->has_subquery()` at `sql_resolver.cc:6515`; post-transform `new_item->update_used_tables()` at `sql_resolver.cc:6545`; target `Item_func::update_used_tables()` resets `m_accum_properties` at `sql/item_func.cc:708-719`. The object processed by the target operation is the post-replacement `Item_func` root of the `WHERE`/`JOIN`/`SELECT` expression. The sensitive input is a scalar subquery inside a function/operator so the root carries `PROP_SUBQUERY` before replacement and no descendant subquery after. The observable is residual `has_subquery()` behavior (optimizer trace / EXPLAIN subquery handling). Row-result impact is not established.
- C2: `Item_func_isnull::update_used_tables()` at `sql/item_cmpfunc.cc:5957-5970`; downstream `has_wf()` consumers at `sql/sql_select.cc:4106-4123` and `4139-4145`. The object processed is the `IS NULL` wrapper whose child is a non-nullable window-function expression. Sensitive input: non-nullable `wf_expr OVER (...)` child so parent skips propagation and target propagates `PROP_WINDOW_FUNCTION`. Observable: value of `IS NULL(wf_expr OVER (...))` under a buffered window vs. the independent oracle (window result over original rows, then `IS NULL`).

Implementation candidates (not source-confirmed):
- The exact plan that reaches `needs_buffering()`/`CreateFramebufferTable()` for C2 is unresolved; T2–T5 use window queries with `ORDER BY`/frame that plausibly require buffering, but the plan trace is not established.
- The downstream `has_subquery()` consumer for C1 is not shown; T1 is exploratory and its row output is not predicted to differ.

Shortfall: only C1 and C2 are defensible; C3 lacks a downstream consumer. Five distinct supported candidates are not available. T1–T5 below cover C1 (two variants on different expression positions: WHERE and SELECT) and C2 (three variants on different non-nullable window children and frame conditions). These are not five independent candidates; they are two candidates with position/boundary variants, and the shortfall is stated.

```sql
-- T1 (C1, exploratory): scalar subquery inside a WHERE function; post-replacement root is Item_func.
-- Sensitive: root has PROP_SUBQUERY before replacement, none after. Observable: residual has_subquery() in trace/EXPLAIN.
CREATE DATABASE IF NOT EXISTS s2_c1;
USE s2_c1;
DROP TABLE IF EXISTS t1_outer, t1_inner;
CREATE TABLE t1_outer (id INT PRIMARY KEY, v INT NOT NULL);
CREATE TABLE t1_inner (id INT PRIMARY KEY, w INT NOT NULL);
INSERT INTO t1_outer VALUES (1,10),(2,20),(3,30);
INSERT INTO t1_inner VALUES (1,5),(2,25),(3,35);
-- Target: WHERE expression is a function over a scalar subquery.
SELECT id, v FROM t1_outer
 WHERE (v + (SELECT w FROM t1_inner WHERE t1_inner.id = t1_outer.id)) > 20;
-- Contrast: same predicate without subquery (no replace_subquery_in_expr path).
SELECT id, v FROM t1_outer WHERE v + 5 > 20;
-- Diagnostic: trace to inspect residual subquery handling on the post-replacement item.
SET optimizer_trace='enabled=on';
SELECT id, v FROM t1_outer
 WHERE (v + (SELECT w FROM t1_inner WHERE t1_inner.id = t1_outer.id)) > 20;
SELECT TRACE FROM information_schema.OPTIMIZER_TRACE;
SET optimizer_trace='enabled=off';
DROP TABLE t1_outer, t1_inner;
```

```sql
-- T3 (C2): IS NULL over a non-nullable window-function child in a buffered window.
-- Sensitive: child is non-nullable (SUM OVER with frame over NOT NULL column) so parent skips propagation;
-- target propagates PROP_WINDOW_FUNCTION to the IS NULL wrapper. Oracle: window result over original rows, then IS NULL.
USE s2_c1;
DROP TABLE IF EXISTS t3_w;
CREATE TABLE t3_w (id INT PRIMARY KEY, g INT NOT NULL, x INT NOT NULL);
INSERT INTO t3_w VALUES (1,1,10),(2,1,20),(3,2,30),(4,2,40),(5,1,50);
-- Target: IS NULL wrapper around a window function.
SELECT id, g, x,
       IS NULL(SUM(x) OVER (PARTITION BY g ORDER BY id ROWS BETWEEN 1 PRECEDING AND CURRENT ROW)) AS isn
  FROM t3_w ORDER BY id;
-- Contrast: bare window function (no IS NULL wrapper) — same window, no wrapper property question.
SELECT id, g, x,
       SUM(x) OVER (PARTITION BY g ORDER BY id ROWS BETWEEN 1 PRECEDING AND CURRENT ROW) AS s
  FROM t3_w ORDER BY id;
DROP TABLE t3_w;
```

3. Expected results and path observations

T1 (C1, exploratory): Target query returns rows (1,10) [10+5=15, not >20 → excluded], (2,20) [20+25=45 >20 → included], (3,30) [30+35=65 >20 → included], i.e. rows (2,20),(3,30). Contrast returns (2,20),(3,30) as well (20+5=25>20, 30+5=35>20; 10+5=15 excluded). Row outputs match; this does not establish the property mapping. What must be observed: in the optimizer trace, whether the post-replacement `Item_func` root still reports `has_subquery()==true` (parent) or `false` (target). No execution or trace has been captured; the residual-subquery consumer is not shown in Stage 1, so no row-visible parent/target difference is predicted.

T2 (C1, exploratory): Target SELECT returns (1,15),(2,45),(3,65); contrast returns (1,15),(2,25),(3,35). Row outputs differ only because the subquery values differ from the constant 5 — this is not the property effect. The property observation is again the trace-level `has_subquery()` on the post-replacement SELECT-list item. No execution claimed.

T3 (C2): Oracle per row (window over original rows, then IS NULL): id1 g1 x10 → SUM over {10}=10 → IS NULL=0; id2 g1 x20 → SUM over {10,20}=30 → 0; id5 g1 x50 → SUM over {20,50}=70 → 0; id3 g2 x30 → SUM over {30}=30 → 0; id4 g2 x40 → SUM over {30,40}=70 → 0. All `isn` values are 0 because SUM over NOT NULL is non-null. Target query is expected to return these values if materialization preserves semantics; a parent/target difference would appear as a non-zero `isn` or a wrong `s`/`x` restored value under buffering. What must be observed: whether the plan reaches `needs_buffering()`/`CreateFramebufferTable()` and whether the `IS NULL` wrapper is filtered from `fb_fields` (target) or retained (parent). The plan trace is not established by Stage 1; no execution claimed.

T4 (C2): Oracle: id1 g1 x10 → SUM {10}=10 → 0; id2 g1 x20 → SUM {10,20}=30 → 0; id5 g1 x50 → SUM {10,20,50}=80 → 0; id3 g2 x30 → 30 → 0; id4 g2 x40 → 70 → 0. Same all-zero `isn` expectation; the different frame changes the buffering boundary, not the nullability. Observation target is the same `has_wf()` filtering in the framebuffer. No execution claimed.

T5 (C2): Oracle: COUNT over NOT NULL is non-null, so `isn` is 0 for every row: id1→1, id2→2, id5→2, id3→1, id4→2 (counts), all `isn=0`. Contrast `c` column shows those counts. A parent/target difference would manifest as a wrong restored `c`/`x` or a non-zero `isn` under buffering. Observation target: same `has_wf()` filtering; child item type differs (COUNT vs SUM) but the sensitive property is identical. No execution claimed.
