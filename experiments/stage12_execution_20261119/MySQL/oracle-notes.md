# MySQL 结果判读

每份 SQL 按原样在四个提交各运行三轮。离线核验先比较生成目录、输入清单和执行回执的 SQL 哈希，再对照构建记录里的源码提交与两个二进制文件哈希。每轮重新读取原始 XML 和标准错误，检查输出语句是否按输入文件的顺序出现。客户端中途退出时，已经返回的结果会保留，后续未执行的语句不计为成功。

## 差异与归因

核验报告分别记录行值及重复数、行序、显示格式、列名与语句、退出码和错误文本。每个父子边界都要求先检查各侧三轮的稳定性。数值列按数值比较，文本列保留原文，NULL 与空字符串分别处理。MySQL 客户端可能把 BIT(4) 的 `0x01`、`0x02` 直接写入 XML 字段。这会触发 XML 解析错误。核验器仅在字段内可无损还原时解析这些原始字节，并逐轮列出字节值。

诊断比较使用客户端已保存的标准错误，跨轮比较时统一临时库名。原始 SQL 没有请求 `SHOW WARNINGS`，运行记录没有逐语句的服务端警告清单。因此，空的标准错误无法证明聚合查询从未产生服务端警告。

判定指定上游缺陷还要核对独立预期、原始引入与修复两个边界以及上游描述的查询条件。DECIMAL 案例的引入提交本身改变数值精度处理，修复针对比较谓词中的常量替换。脚本中的算术结果随引入提交改变，只能说明该表达式的行为发生变化。

在本目录使用 `python verify.py --output verification.json` 复核全部证据。采集中可加 `--partial` 查询已归档结果。报告中的 `match` 为完整结果匹配，`match_projection` 仅覆盖表中列出的投影，`match_tolerance` 为容差内匹配。完整性失败、SQL 执行错误和预期值不符各自计数。
