# PostgreSQL 原始 SQL 精确版本对照

## 对照结果

四个预先指定的错误结果均未复现。主矩阵共 20 份原始脚本、16 个精确提交、240 次独立执行，80 个脚本与版本组合均三次稳定。全部 20 份脚本在相应目标修复前后的标准输出、标准错误与客户端退出码一致。61 个组合的全部语句成功，19 个组合有 SQL 错误，其中包含针对无效 ICU 规则的预期错误。

| 上游目标 | 引入与修复两条边界的观察 |
|---|---|
| #17335，并行 Append 重复行 | 五份在两条边界均返回预期数据。首次执行计划均没有 Gather 或并行 Append。T4 的两个游标都依次返回 `[10,20]、[10]、[]、[40]、[30]`，原 SQL 注释错估了中间两次取数。 |
| #18522，归并右反连接返回错误行 | 五份在两条边界均返回预期数据。T1、T3、T4、T5 目标执行计划为 Hash Anti Join，T2 使用 NOT IN 子计划。T3、T4 在事务外执行 SET LOCAL，服务端发出警告。T2 两条 SELECT 对 NULL 的过滤本来就不同。 |
| #19533，窗口 COUNT 使用 EXCLUDE 时漏行 | 五份均未包含 EXCLUDE。引入版 T1、T2、T3、T5 使用 WindowAgg 的运行条件并返回预期数据。T4 在引入边界发现另一项已报告的 SQL 拒绝，见下节。本目标修复两侧，五份目标查询和对照均返回预期数据。 |
| #18771，ICU 自定义规则的强度被忽略 | 五份均没有用大小写或重音等数据区分比较强度。父版不识别 RULES / ICU_RULES。引入版 T1 普通排序输出 a,m,z，应用规则后为 m,z,a，T3 建库后同样输出 m,z,a。修复父/子排序一致，T1/T3 随后的目录查询使用历史列名，在两侧均报错。T2 的 FROM 后追加覆盖项语法错误，T4 的空规则与模板的非空规则不兼容，T5 的非法规则按脚本意图被拒绝。 |

## 窗口 T4 独立发现的历史错误

生成的 T4 对五行输入执行 `count(*) OVER ()`，外层保留计数为 5 的行。五行都应返回。引入父版的目标和物化对照均如此。引入版三次执行目标 SELECT 都报 `function with OID 0 does not exist`，同一文件中的物化对照每次都正确返回五行。指定的 #19533 修复前后，目标与对照已同时恢复为五行。

上游另有一项修复，维护者明确追溯到相同的引入提交，修复了窗口值同时单调增、减时未设置比较运算符的遗漏。上游加入了对全窗计数按常量等值过滤的回归测试。[上游修复 53823a06be6f](https://github.com/postgres/postgres/commit/53823a06be6f40d88d8e3ba45045ecee1a21fc5e)

另用未改动的 T4 在这项独立修复的前后各执行三次。父版 `cf112c122060` 三次都在目标查询报告 OID 0，对照均返回五行。修复版 `53823a06be6f` 三次均让目标和对照返回全部五行。证据见 [六次原文回放摘要](secondary_check.json) 和 [两个完整版本](secondary_versions.csv)。这六次单列于主矩阵之外，合计 246 次原文回放、18 个精确提交。

## 数据与运行方式

`versions.csv` 列出四个案例的引入前、引入后、修复前、修复后四个完整 Git SHA。与冻结的 Stage 1 输入及主实验修复表核对。每个案例的 `sql/` 保存 run_20261119_124816 生成的 T1 至 T5 原文。

从 PostgreSQL 上游镜像按完整 SHA 下载源码，校验源码目录名称，分别编译服务端及同版本 psql，启用 ICU。每个版本的 `build.json` 记录下载地址、压缩包和二进制 SHA-256、ICU 版本、编译参数及版本输出。`runtime-version.txt` 记录实际服务端版本、运行 SQL 的数据库角色及权限。

8edd0e79460b 的早期源码使用 ICU 以前默认公开的 TRUE 常量。对该案例四个版本统一传入 ICU 72 提供的兼容编译选项 `-DU_DEFINE_FALSE_AND_TRUE=1`，保留上游源码原文。

每个脚本每侧运行三次。每次从相应版本初始化后干净关闭的数据库集群复制一份，使用专有 Unix 套接字，关闭 TCP 监听。测试角色是独立数据库的所有者，仅有登录和建库权。服务端进程使用非 root 系统用户。ICU 建库脚本可以在私有集群中用 psql 的 `\c` 重连。

所有 SQL 以 psql 文件方式提交，延用逐语句自动提交。第一次开启 auto_explain 记录原查询计划，第二、三次用相同默认查询规划设置运行。`ON_ERROR_STOP=0` 让客户端在 SQL 错误后继续执行原脚本后续语句，psql 的 `\c` 失败仍可能终止文件。每轮的 `status.json` 同时记录客户端退出码和服务端 SQL 错误。空结果集以列名和 `(0 rows)` 保存。

## 文件索引

- `<案例>/<版本角色>/runs/Tn/r1/` 保存首次原始标准输出、标准错误、退出状态、SQL 哈希和带计划的数据库日志；`r2/` 与 `r3/` 保存另外两次执行证据。
- `matrix.csv` 按脚本列出两条提交边界的输出对照、重复次数、SQL 错误与警告。
- `observations.json` 保留各组结果集的列名、顺序、重复行与空结果。
- `expected_check.json` 将三组非 ICU 脚本的实际结果与按输入数据和游标语义独立计算的预期逐组比对。
- `run_versions.py`、`compare_outputs.py`、`check_expected.py` 分别用于原文回放、逐组提取、预期核对。
