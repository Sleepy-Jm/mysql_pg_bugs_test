## T1
候选依据：`sqlite3AtoF` 的 `e != 0` 且有效数 `s` 超过 53 位二进制精度、接近 double 舍入边界时，旧版 long double 路径与目标 Dekker 路径可能给出不同 double。本测试用 SQL 实数文本字面量（`codeReal` → `sqlite3AtoF`）直接进入该路径，并用 `typeof()` 与 `printf('%!.17g', ...)` 观察解析结果；与其他测试的差异在于它只考察“十进制文本 → double”的解析，不涉及输出格式化或整数比较。

```sql
-- 准备：无表，仅用字面量
-- 目标：观察实数文本字面量经 sqlite3AtoF 解析后的 double 值
-- 对照：typeof() 确认是 REAL；printf('%!.17g') 给出可区分位模式的最短/精确表示
SELECT
  typeof(1.234567890123456789e+100)            AS t1_type,
  printf('%!.17g', 1.234567890123456789e+100)  AS t1_val,
  typeof(9.999999999999999999e+18)             AS t2_type,
  printf('%!.17g', 9.999999999999999999e+18)   AS t2_val,
  typeof(1.000000000000000111e+00)             AS t3_type,
  printf('%!.17g', 1.000000000000000111e+00)   AS t3_val;
-- 清理：无对象
```

预期结果（依据 IEEE-754 binary64 round-to-nearest-even 与 SQLite `%!.17g` 语义推导，未执行）：`t1_type='real'`，`t1_val` 为 `1.234567890123456789e+100` 按 binary64 舍入后的 17 位有效数字表示（约 `1.2345678901234568e+100`）；`t2_type='real'`，`t2_val` 为 `9.999999999999999999e+18` 舍入后的值（约 `1.0e+19`，具体末位需 oracle 确认）；`t3_type='real'`，`t3_val` 为 `1.000000000000000111` 舍入后的值（约 `1.0000000000000002`）。仍需以后验证：`printf('%!.17g')` 是否完全绕过 `sqlite3FpDecode` 的舍入差异，以及 `codeReal` 是否确实对每个字面量调用 `sqlite3AtoF`。

## T2
候选依据：`sqlite3AtoF` 的溢出/次正规边界路径。旧版有显式 `r > DBL_MAX` 检查，目标版依赖 Dekker 乘法与 `sqlite3IsNaN` 兜底；接近 `DBL_MAX` 与接近最小次正规数的文本字面量可能产生不同 double。与其他测试的差异在于它专门考察极端指数范围（溢出与下溢），而非普通精度边界。

```sql
-- 准备：无表
-- 目标：观察接近 DBL_MAX 与次正规边界的实数文本字面量解析
-- 对照：typeof() 与 printf('%!.17g') 观察是否得到 Inf/0/次正规
SELECT
  typeof(1.7976931348623157e+308)              AS a_type,
  printf('%!.17g', 1.7976931348623157e+308)    AS a_val,
  typeof(1.7976931348623159e+308)              AS b_type,
  printf('%!.17g', 1.7976931348623159e+308)    AS b_val,
  typeof(4.9406564584124654e-324)              AS c_type,
  printf('%!.17g', 4.9406564584124654e-324)    AS c_val,
  typeof(2.4703282292062327e-324)              AS d_type,
  printf('%!.17g', 2.4703282292062327e-324)    AS d_val;
-- 清理：无对象
```

预期结果（依据 binary64 语义推导，未执行）：`a_type='real'`，`a_val` 为 `1.7976931348623157e+308` 舍入后的最大有限 double（约 `1.7976931348623157e+308`）；`b_type='real'`，`b_val` 为 `Inf`（因超出 DBL_MAX 舍入阈值）；`c_type='real'`，`c_val` 为最小正次正规数（约 `4.9406564584124654e-324`）；`d_type='real'`，`d_val` 为 `0.0`（低于最小次正规数一半）。仍需以后验证：SQLite 对溢出字面量是否返回 `Inf` 还是报错，以及 `printf` 对 `Inf`/次正规数的格式化是否稳定。

## T3
候选依据：`sqlite3FpDecode` 的缩放循环路径。目标版固定使用 double-double 且阈值改为 `9.223...e+18` 系列，旧版 long double 使用 `1.0e+19` 系列；对需要多次缩放的大/小 double，`printf('%f')` 或 `printf('%e')` 的输出末位可能不同。与其他测试的差异在于它考察“double → 十进制文本”的输出路径，而非解析路径。

```sql
-- 准备：无表
-- 目标：观察大/小 double 经 sqlite3FpDecode 缩放后的文本输出
-- 对照：同一 double 用 %e 与 %f 两种格式，观察末位是否一致
SELECT
  printf('%.17e', 1.0e+300)                    AS big_e,
  printf('%.17e', 1.0e-300)                    AS small_e,
  printf('%.17e', 9.223372036854775808e+18)    AS near_2p63_e,
  printf('%.17e', 1.2345678901234567e+200)     AS mid_e,
  printf('%.17f', 1.0e-300)                    AS small_f;
-- 清理：无对象
```

预期结果（依据 binary64 精确值与 `%e`/`%f` 舍入语义推导，未执行）：`big_e` 为 `1.0e+300` 的 17 位有效数字表示（约 `1.00000000000000000e+300`）；`small_e` 为 `1.0e-300` 的 17 位表示（约 `1.00000000000000000e-300`）；`near_2p63_e` 为 `2^63` 的精确值 `9.223372036854775808e+18`；`mid_e` 为 `1.2345678901234567e+200` 的 17 位表示；`small_f` 为 `1.0e-300` 的定点表示（约 `0.000...` 共 300 位小数）。仍需以后验证：`printf` 的 `%e`/`%f` 是否严格复用 `sqlite3FpDecode`，以及 `CAST(real AS TEXT)` 是否走同一路径。

## T4
候选依据：`sqlite3IntFloatCompare` 的整数与浮点比较路径。目标版删除 long double 分支，改为范围拦截 + `(i64)r` + `(double)i` 比较；当 `i` 超过 `2^53` 且 `r` 接近 `2^63` 或 `-2^63` 边界时，可能产生不同比较结果。与其他测试的差异在于它考察混合 INTEGER/REAL 比较，而非解析或格式化。

```sql
-- 准备：创建表并插入 INTEGER 与 REAL 混合值
CREATE TABLE t4(i INTEGER, r REAL);
INSERT INTO t4 VALUES
  (9223372036854775807, 9.223372036854775808e+18),  -- i = 2^63-1, r = 2^63
  (9223372036854775807, 9.223372036854775807e+18),  -- r 略小于 2^63
  (-9223372036854775808, -9.223372036854775808e+18),-- i = -2^63, r = -2^63
  (9007199254740993, 9007199254740992.0),           -- i = 2^53+1, r = 2^53
  (9007199254740993, 9007199254740994.0);           -- i = 2^53+1, r = 2^53+2
-- 目标：观察 INTEGER 与 REAL 比较结果
SELECT i, r,
       (i < r) AS lt,
       (i = r) AS eq,
       (i > r) AS gt
FROM t4
ORDER BY i, r;
-- 清理
DROP TABLE t4;
```

预期结果（依据精确有理数比较推导，未执行）：第 1 行 `i=2^63-1 < r=2^63`，故 `lt=1, eq=0, gt=0`；第 2 行 `r` 略小于 `2^63` 但仍大于 `2^63-1`（因 `2^63-1` 与 `2^63` 之间无其他 double），故 `lt=1`；第 3 行 `i=-2^63 = r=-2^63`，故 `eq=1`；第 4 行 `i=2^53+1 > r=2^53`，故 `gt=1`；第 5 行 `i=2^53+1 < r=2^53+2`，故 `lt=1`。仍需以后验证：SQLite 是否将 `i` 保持为 INTEGER 而非转为 REAL，以及 `ORDER BY` 是否触发额外比较路径。

## T5
候选依据：`sqlite3AtoF` 的 `e == 0` 路径。旧版直接 `*pResult = s`，目标版执行 Dekker 加法 `rr[0]+rr[1]`；虽然通常等价，但代码形式已变，且 `s` 接近 `2^53` 或 `2^63` 时 residual 可能非零。与其他测试的差异在于它专门考察无指数（`e == 0`）的纯整数文本字面量解析，而非带指数或极端范围。

```sql
-- 准备：无表
-- 目标：观察无指数实数文本字面量（e == 0 路径）的解析
-- 对照：typeof() 与 printf('%!.17g') 观察 s 接近 2^53/2^63 时的 residual
SELECT
  typeof(9007199254740993.0)                   AS a_type,
  printf('%!.17g', 9007199254740993.0)         AS a_val,
  typeof(9223372036854775807.0)                AS b_type,
  printf('%!.17g', 9223372036854775807.0)      AS b_val,
  typeof(18446744073709551615.0)               AS c_type,
  printf('%!.17g', 18446744073709551615.0)     AS c_val;
-- 清理：无对象
```

预期结果（依据 binary64 舍入语义推导，未执行）：`a_type='real'`，`a_val` 为 `9007199254740993` 舍入到最近 double 的结果（`2^53+1` 不可精确表示，舍入到 `2^53` 或 `2^53+2`，需 oracle 确认 tie 规则）；`b_type='real'`，`b_val` 为 `9223372036854775807` 舍入后的 double（约 `9.223372036854775808e+18`）；`c_type='real'`，`c_val` 为 `18446744073709551615` 舍入后的 double（约 `1.8446744073709552e+19`）。仍需以后验证：`e == 0` 路径下 Dekker 加法是否产生与 `(double)s` 不同的 residual，以及 `printf('%!.17g')` 是否暴露该差异。

缺口说明：以上五个测试覆盖了交接中列出的三条主要路径（`sqlite3AtoF` 的 `e != 0`、溢出/次正规、`e == 0`；`sqlite3FpDecode` 的缩放；`sqlite3IntFloatCompare` 的边界比较）。仍缺少的证据包括：完整 SQL→VDBE 调用图、`CAST(real AS TEXT)` 是否复用 `sqlite3FpDecode`、`printf` 各格式的舍入细节、以及旧版 long double 在各平台的实际启用条件。这些缺口意味着上述测试的预期值需以独立 oracle（如 Python `float`/`Fraction`/`format`）校准后才能作为判定依据。
